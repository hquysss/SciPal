# Bạn bè (Plan A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Học sinh tìm người, gửi/nhận lời mời kết bạn, xem và huỷ danh sách bạn, từ một mục "Cộng đồng" trong menu tài khoản.

**Architecture:** Bảng `friendships` (RLS chỉ SELECT cho thành viên), mọi ghi đi qua route Fastify `friends.ts` bằng service_role. Frontend gọi API bằng `authoringCall`, trang `/community` chứa `FriendsTab`; NavBar có mục Cộng đồng kèm chấm đỏ khi có lời mời nhận được.

**Tech Stack:** Supabase Postgres + RLS, Fastify 4 + vitest, Next.js 15 + vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-10-12-friends-design.md` (phần Plan A). Plan B (chat) làm sau, ngoài plan này.

## Global Constraints

- Ghi chỉ qua backend; client chỉ SELECT qua RLS (Invariant 4, 5). Không đưa `SUPABASE_SERVICE_ROLE_KEY` vào `frontend/`.
- Cặp bạn lưu `user_a < user_b` (so sánh chuỗi uuid). Unique `(user_a, user_b)`.
- Lỗi backend: `{ error: <vi>, error_en: <en> }` như `backend/src/routes/profile.ts`.
- Tối đa **20** lời mời `pending` đang gửi đi mỗi user. `q` tìm kiếm ≥ **2** ký tự, tối đa **10** kết quả.
- Song ngữ qua `t({ en, vi })`; không hard-code màu môn học.

## Review Focus

- `q` chứa `%` hoặc `_`: không được khớp mọi người (escape trước `ilike`). Test ở Task 2.
- A và B gửi lời mời cho nhau gần như cùng lúc: request thứ hai tự accept, không 409, không tạo dòng thứ hai. Test ở Task 3.
- Người gửi lời mời tự accept lời mời của chính mình: 403. Test ở Task 3.
- Người ngoài xoá/accept dòng của người khác: 404, không lộ sự tồn tại. Test ở Task 3.
- Hồ sơ không có `display_name` (null): UI hiển thị tên dự phòng, không vỡ. Test ở Task 4.

  - `export const friendRoutes: FastifyPluginAsync`
  - `export function orderPair(a: string, b: string): [string, string]` — trả cặp đã sắp `[nhỏ, lớn]`.
  - `type FriendEntry = { id: string; user_id: string; display_name: string | null; avatar_url: string | null }`
  - `GET /api/friends` → `{ friends: FriendEntry[]; incoming: FriendEntry[]; outgoing: FriendEntry[] }` (`id` là id dòng friendship, `user_id` là người kia).
  - `GET /api/friends/search?q=` → `{ users: Array<{ user_id: string; display_name: string | null; avatar_url: string | null; relation: 'none' | 'friend' | 'pending_out' | 'pending_in'; friendship_id: string | null }> }`

- [ ] **Step 1: Viết test** trong `friends.test.ts` (dựng app như `accounts.test.ts`: Fastify + `app.decorate('supabase', mock)` + hook gắn `req.user`). Test:
  - `orderPair('b','a')` bằng `['a','b']` và `orderPair('a','b')` bằng `['a','b']`.
  - `GET /api/friends` trả 503 khi không có supabase; trả 401 khi không có user.
  - `GET /api/friends` phân loại đúng: dòng `accepted` → `friends`; `pending` với `requested_by` khác mình → `incoming`; `pending` do mình gửi → `outgoing`; `user_id` luôn là người kia.
  - `GET /api/friends/search?q=a` (1 ký tự) → 400; `q` có `%` hoặc `_` được escape thành `\%`, `\_` trước khi đưa vào `ilike` (kiểm đối số mock); kết quả không chứa chính mình và có `relation` đúng.

Lấy dòng friendship của mình bằng `.or(\`user_a.eq.${id},user_b.eq.${id}\`)`, rồi lấy `profiles(id, display_name, avatar_url)` của những người kia bằng một truy vấn `.in('id', ids)`. Search: `profiles.display_name ilike %q%`, `.neq('id', me).limit(10)`, rồi đối chiếu `relation` với các dòng friendship của mình.

### Task 3: Backend — gửi, chấp nhận, xoá

**Files:**
- Modify: `backend/src/routes/friends.ts`, `backend/src/routes/friends.test.ts`

**Interfaces:**
- Consumes: `orderPair`, `friendRoutes` từ Task 2.
- Produces:
  - `POST /api/friends/request` body `{ user_id: string }` → `201 { id: string; status: 'pending' | 'accepted' }`
  - `POST /api/friends/:id/accept` → `200 { id: string; status: 'accepted' }`
  - `DELETE /api/friends/:id` → `200 {}`

- [ ] **Step 1: Viết test** (mỗi cái là một `it`):
  - request: `user_id` bằng chính mình → 400; `user_id` không phải uuid → 400; người kia không có trong `profiles` → 404; đã tồn tại dòng (đã bạn hoặc mình đã gửi) → 409; người kia **đã gửi** cho mình → 200 `status: 'accepted'` và gọi `update`, không `insert`; mình đã có 20 lời mời `pending` gửi đi → 429; bình thường → 201 `pending`, `insert` được gọi với `user_a < user_b` và `requested_by` là mình.
  - accept: dòng không tồn tại hoặc mình không phải thành viên → 404; mình là `requested_by` → 403; dòng đã `accepted` → 409; bình thường → 200.
  - delete: không phải thành viên → 404; thành viên → 200 và `delete` được gọi đúng id.
- [ ] **Step 2: Chạy**: Expected: FAIL.
- [ ] **Step 3: Implement** ba route. Validate uuid bằng regex như `UUID_PATTERN` trong `classes.ts`. Đếm 20 lời mời bằng `select('id', { count: 'exact', head: true }).eq('requested_by', me).eq('status','pending')`. Insert xung đột unique (`error.code === '23505'`) cũng trả 409 để chịu được hai request đồng thời. Với accept chéo, thao tác `update ... eq('status','pending')` để request đồng thời không accept hai lần.
